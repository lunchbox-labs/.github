# npm package conventions

- Follow the repository's declared package manager, committed lockfile, and reproducible installation command. For npm-managed repositories, use `package-lock.json` and `npm ci`. Use the Node version supported by the repository and its CI configuration.
- Use the existing package scripts for typechecking, linting, formatting checks, tests, and builds. Inspect what the aggregate check script covers; run applicable package or native integration tests separately when they are not included.
- Verify changes to package exports, included files, or build output through packed-package tests when available. Keep package metadata and user-facing installation examples consistent with the published interface.
- Keep the package version and any corresponding root package version entries in the lockfile aligned where that metadata exists. The existing stable-release convention is a `v`-prefixed tag matching `package.json`'s semantic version. Do not bump the version solely for documentation changes unless the repository's release convention requires it.
- In CI, cache `node_modules` as the workflow conventions describe rather than only npm's download cache; native modules such as node-pty compile from source on Linux, so a warm download cache still leaves `npm ci` slow. `npm run check` stays the local aggregate; CI may run its parts separately so that platform-independent checks run once.
- Preserve repository-specific release validation and publishing configuration. Package access, provenance, compatibility baselines, and integration commands belong in the package repository rather than shared defaults.
